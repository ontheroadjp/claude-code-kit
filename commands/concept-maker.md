# /concept-maker

`docs/.ai/l0_candidates.md` に溜まった L0（`docs/L0_concept/concept.md`・`policy.md`）昇格候補を、ユーザーとの壁打ちを経て L0 へ追記する専用のスタンドアロン入口です。

- `/work`・`/task`・`/patch`・`/docs-sync`・`/init-docs` とは独立したワークフローです
- **L0 への書き込みは常にこのコマンド（または `/init-docs` の初回新規作成時）を経由します。それ以外の経路（`/task`・`/patch`・`/docs-sync`）は L0 に一切書き込みません**
- 機械的な自動追記は行いません。候補ごとにドラフト提示 → ユーザーの修正 → 再提示のラウンドを経て、明示的な承認を得てから追記します
- 追記は既存内容の書き換えではなく末尾への追加が基本です
- 処理した候補はキューから削除します

---

## ワークフロー

### Step 0: 前提確認

- `.git/` が存在すること（存在しない場合: 終了）
- 現在ブランチが `main` であること
    - main でない場合: 現在の作業を報告し、`main` へ切り替えてから再実行するようユーザーに促して終了する
- `git status --porcelain` が空であること
    - 空でない場合: 未コミット変更の扱いをユーザーに確認する（stash して退避 / 中断）。`/work` の G-2 と同じ選択肢を提示する
- `docs/.ai/l0_candidates.md` の存在と中身を確認する
    - 存在しない、または候補が 0 件の場合: 「対応可能な L0 昇格候補はありません」と報告して終了する

### Step 1: 候補の一覧提示

キュー内の全候補を一覧表示する:

```
## L0 Promotion Candidates (N)

1. <source>:<line-range> — <一行要約> (issue #<N>)
2. ...
```

処理順（上から順）をユーザーに確認する。ユーザーが順序変更・一部スキップを希望する場合は従う。

### Step 2: 候補ごとの壁打ち（1件ずつループ）

各候補について以下を行う:

1. 候補の `source`（L3 doc の該当行範囲）を Read し、文脈・根拠を把握する
2. `docs/L0_concept/concept.md`（プロダクトの目的・解決する問題・対象ユーザー・設計上の制約）と `docs/L0_concept/policy.md`（技術選定・セキュリティ・運用/性能・禁止事項・整合性の各方針）のどちらに追記すべきかを、理由とともに提示する
3. 追記文のドラフトを提示する（対象ファイルの既存の記述形式・粒度に合わせる。根拠として候補の `source` を引用する形にする）
4. ユーザーからのフィードバックを受けて修正し、再提示する。**1回のドラフト提示で終わらせず、ユーザーが「これでよい」と明示するまで繰り返す**
5. ユーザーから明示的な承認（例:「これで追記して」「OK」）を得たら、確定した文言と追記先ファイルを記録し、次の候補へ進む
6. ユーザーが見送り（skip）を選んだ場合:
    - キューからその候補を削除するか、次回に持ち越すかをユーザーに確認する
    - 削除する場合は Step 3 での追記対象から除外し、キューからも取り除く
    - 持ち越す場合はキューに残したまま次の候補へ進む

全候補の処理（承認・見送りいずれか）が終わるまでこの Step を繰り返す。

### Step 3: ブランチ作成・追記・commit

承認された候補が 1 件もない場合はこの Step をスキップし、Step 4 へ進む。

1. `git checkout -b concept/<YYYYMMDD>` でブランチを作成する（同名ブランチが既に存在する場合はユーザーに確認する）
2. Step 2 で承認された候補を、対応する L0 ファイル（`concept.md` または `policy.md`）の末尾に追記する。各追記に `根拠: <source>` を添える
3. 追記した候補（および Step 2 で削除が確定した見送り候補）を `docs/.ai/l0_candidates.md` から削除する。キューが空になった場合はファイル自体を削除する
4. `/git-commit` を実行する（パラメータ: `issue_number=none`, `allowed_types=[docs]`）

### Step 4: 報告

変更内容サマリ（追記した候補・見送った候補・キューに残った候補）と、以下の fast-forward merge 手順をユーザーに報告する:

```bash
git checkout main
git merge --ff concept/<YYYYMMDD>
git push origin main
git branch -d concept/<YYYYMMDD>
```

L0 は特に慎重な扱いを要するため、`/patch` と異なり merge 前に `git diff main concept/<YYYYMMDD> -- docs/L0_concept/` で最終差分を必ず確認するようユーザーに促す。

報告後、`git checkout main` で main に戻る。

---

## なぜ issue・PR を作らないか

L0 への変更は他のどの docs 更新よりもユーザー自身の判断が主体であるべきであり、Step 2 の壁打ちと明示的承認そのものが実質的なレビュープロセスを兼ねる。`/patch` と同様、軽量な branch + commit + ユーザー手動 ff-merge の形にすることで、承認の主体が最後までユーザー自身であることを保つ。

## なぜ機械的な一括生成をしないか

L0 はプロジェクトの最も核となる意思決定の記録であり、将来的に自然言語のラフな指示から AI が自律的に実装を進める際の指針になる想定である。曖昧・不正確な文言が紛れ込むと、その後の AI の判断がユーザーの意図から外れる原因になる。したがって、候補ごとに個別の壁打ちを行い、要約や機械的な言い換えで済ませない。

## スコープ外

- L0 昇格候補の検知（`/docs-sync` が担う）
- L0 の新規作成（リポジトリに L0 が存在しない場合。`/init-docs` が担う）
- 実装・コード変更（`/work`・`/task`・`/patch` が担う）
