# /mtg

`agenda` label が付いた GitHub issue を、人間と AI agent が対話して進めるための workflow です。通常は `/work #N` から委譲されます。

この workflow の目的は、実装前の方向性・優先順位・フェーズ・実装範囲を、人間が意思決定できる状態にすることです。固定的な段階遷移は強制しません。必要に応じて前の論点へ戻り、方向性、フェーズ、詳細、スコープ外、保留を自由に往復します。

## 境界

- リポジトリと GitHub の状態は、ユーザーが明示的に指示するまで読み取り専用で扱う
- AI は事実、選択肢、リスク、暫定案を提示するが、方向性・優先順位・実装範囲・終了を決定しない
- 実装、branch 作成、commit、push、PR 作成、`/task`、`/patch`、`/docs-sync`、`/git-pr` へは委譲しない
- `/new-issue` は、ユーザーが明示的に実行を指示した場合にのみ実行する。提案や合意だけを根拠に自動実行してはならない
- ユーザーが close を宣言するまで agenda を終了しない。AI が十分な議論が済んだと判断して自動終了してはならない

## ワークフロー

### Step 0: 入力と認証の確認

- issue 番号が指定されていない場合は、番号を尋ねて待機する
- `gh auth status` で GitHub CLI が利用可能であることを確認する
- 認証されていない場合は、`gh` にログインしてから再実行するよう報告して終了する

### Step 1: agenda issue の取得と検証

以下で対象 issue を取得する:

```bash
gh issue view <番号> --json number,title,body,labels,url,state
```

- 取得に失敗した場合はエラーを報告して終了する
- label の name が `agenda` と完全一致することを確認する
- `agenda` label がない場合は、対象外であることを報告して終了する。label の追加や他 workflow への切り替えは行わない
- title、body、state、labels、URL を対話の起点として保持する

### Step 2: 対話的な検討

issue の目的、制約、既知の事実を起点に、人間との対話を進める。以下は必要に応じて扱う観点であり、順序や全項目の実施を強制しない:

- 解決したい問題、成功条件、制約、許容できるリスク
- 全体の方向性と代替案
- 価値・依存関係・リスクに基づくフェーズ分割
- 各フェーズの in scope / out of scope、完了条件、検証方法、ロールバックまたは中止条件
- 未決事項、追加調査、保留事項
- 実装しないと決める選択肢

根拠が必要な場合は、`docs/.ai/repo.profile.json`、`primary_docs.investigation`、issue が言及するファイルの順に、必要な範囲だけを Read する。事実、評価、意見、提案を混同しない。具体化が必要になったフェーズでは、次の形式で整理して人間の判断を求める:

- **Facts**: 直接確認できた事実
- **Assessment**: 事実から得られる評価
- **Opinions**: AI の見解と代替案
- **Proposals**: 人間が選択できる具体的な提案

人間の合意がない内容を決定事項として扱わない。

### Step 3: 実装 issue 化

実装に進める合意済みの単位が生まれた場合、AI は `/new-issue` で起案できることを案内できる。

- ユーザーが `/new-issue` の実行を明示的に指示した場合のみ、`commands/new-issue.md` を Read して実行する
- `/mtg` は `/new-issue` を自動実行・自動委譲しない
- `/new-issue` には、対話で人間が合意した内容だけを引き渡す。未合意または不明な項目を推測で補わない
- issue 作成後も、ユーザーが close を宣言するまでは `/mtg` を終了しない

### Step 4: close

ユーザーが agenda issue の close を明示的に宣言した場合だけ、以下を整理して提示する:

- 合意した目的・方向性
- 決定事項
- 今回スコープ外にしたことと理由
- 未決事項・保留事項
- 起案済み／これから起案する実装 issue
- 実装しないと決めた項目
- 次回再開時の論点

ユーザーがこの要約と close を明示的に確認した場合のみ、issue に最終要約をコメントし、issue を close する。ユーザーが close を撤回または修正した場合は Step 2 に戻る。
